## 2. Plataforma y almacenamiento requeridos

### PHP, Composer y Node

**Estado observado:** CLI 8.4.27 con GD JPEG/PNG/WebP; servicios PHP-FPM 8.4/8.5 activos, sin asignación del sitio comprobada. Composer ausente y Node 18.20.8 incompatible. Son pendientes concretos de preparación; no se ejecutan instalaciones, cambios de versión ni selección de pools en esta tarea.

- `composer.json` exige PHP **`^8.2`** y Laravel `^12.0`; `composer.lock` fija Laravel **12.69.2**. Elegir una rama PHP mantenida y compatible con **todo el lock**, no solo con el mínimo del framework. Hay dependencias bloqueadas con techo de PHP 8.5: no se certifica una rama futura por cumplir `^8.2`. Registrar versión exacta, parches y módulos tanto del PHP web como de CLI, cron y posibles workers.
- Requisitos base Laravel: Ctype, cURL, DOM, Fileinfo, Filter, Hash, Mbstring, OpenSSL, PCRE, PDO, Session, Tokenizer y XML. El lock de ejecución incluye también Iconv, JSON y Libxml. Algunas capacidades son integradas según la versión; comprobarlas, no asumir nombres de paquetes del SO.
- Añadir explícitamente **`pdo_mysql`** para MySQL remoto y **GD con lectura/escritura JPEG, PNG y WebP**, más Fileinfo. GD y `pdo_mysql` no quedan certificados únicamente por `composer check-platform-reqs`. La aplicación decodifica/recodifica imágenes con GD; no requiere Imagick. SQLite/PDO SQLite corresponde a la suite aislada, no a la conexión remota elegida.
- Comprobación futura: `composer check-platform-reqs --no-dev` sobre el artefacto exacto y diagnóstico privado HTTP mínimo del SAPI web, sin `phpinfo()`, `php -i`, variables de entorno o secretos. OPcache es una optimización a evaluar, no una extensión instalada confirmada. ZIP/unzip/Git y procesos de CLI/cron son requisitos de herramientas que dependen del método de build elegido; verificar por separado.
- `package-lock.json` fija **Vite 7.3.6** y **laravel-vite-plugin 2.1.0**. Ambos declaran Node **`^20.19.0 || >=22.12.0`**. Seleccionar una versión mantenida dentro de esa condición y fijar Node/npm exactos para reproducir el build. No suponer que cualquier Node 20 o 22 sirve.
- Compilar en un entorno de build separado con `npm ci` y `npm run build`, previa revisión de scripts/entorno. Usar dependencias de desarrollo en build, no un `npm ci --omit=dev` que elimina Vite. La aplicación sirve el resultado estático: Node/Vite no necesitan mantenerse como servidor público. Publicar solo `public/build`/manifest correspondientes al artefacto; excluir `node_modules`, `public/hot` y servidor de desarrollo. `VITE_*` se incorpora al cliente: nunca contendrá secretos.
- Composer debe estar disponible en build o mediante un proceso compatible aprobado. La instalación futura usa lock, no `composer update`; revisar hooks, incluyendo `package:discover`. No utilizar `composer setup`: genera entorno/clave y ejecuta migraciones. No utilizar `composer test` con configuración normal: limpia cachés y arranca Artisan; para comprobaciones locales, usar el aislamiento documentado en fase 1.

Los mínimos y el front controller coinciden con la [documentación oficial de despliegue de Laravel 12](https://laravel.com/docs/12.x/deployment). La condición Node coincide con la [guía de Vite 7](https://v7.vite.dev/guide/); el lock del repositorio es la referencia exacta de este artefacto. No se propone actualizar dependencias durante esta planificación.

- Partir del **Nginx activo `clp-nginx` en Ubuntu 22.04.5 LTS**; `apache2` no aparece disponible en la observación. CloudPanel 2.5.4-2+clp-jammy está confirmado por el inventario de paquetes compartido; comprobar la gestión y configuración del sitio desde su interfaz antes de definir el procedimiento de vhosts. Usuario PHP con lectura del código; escritura únicamente en `storage/`, `bootstrap/cache/` y temporales de subida que realmente necesite. Propietarios/grupos/ACL y modos exactos se fijarán con el operador después de conocer el SO; no `777`, permisos globales ni escritura sobre todo el release.
- `config/filesystems.php` define `report_photos`: local, privado, `serve=false`, raíz `storage/app/report-photos`. `config/reports.php` permite seleccionar el disco mediante `REPORT_PHOTOS_DISK`. Los objetos actuales quedan bajo `reports/photos/` dentro de esa raíz. **No crear un enlace público para este disco ni usar el disco `public`.** No hay un bucket remoto configurado/certificado por este plan.
- Acordar una carpeta persistente **exclusiva de staging**, mantenida entre releases y fuera de `public/`; resolver su enlace/disposición sin cambiar el modelo de privacidad. La misma ruta debe ser accesible por PHP web, CLI y scheduler con sus identidades de servicio. Si hubiera varias instancias, definir almacenamiento compartido antes de aprobar; no basta disco local de una instancia.
- Fotos por `GET /reportes/fotos/{photo}`: auth, sesión actual, cuenta activa/verificada, roles/propietario y límite de frecuencia. Respuesta privada `no-store`, `nosniff`, no URL estática. Confirmar que proxy/CDN no cachea estas respuestas y que `/storage/...` no expone ese directorio.

Definir límites PHP (`upload_max_filesize`, `post_max_size`, `max_file_uploads`, memoria/tiempos), web/proxy y espacio temporal coherentes con 5 archivos más multipart. El presupuesto GD usa aproximadamente 16 bytes/píxel más entrada y margen; medirlo en el SAPI real. No rebajar validaciones para que pase una carga ni fijar valores de RAM sin evidencia.
- Respaldar juntos base y fotos privadas. El borrado lógico de cuentas conserva atribución y archivos. La eliminación autorizada de reportes usa una tabla durable de limpieza; una cascada SQL o borrar archivos por fecha no sustituye ese flujo.

## 5. Procedimiento futuro por puertas de control

**Ninguna acción de esta sección se ejecutó.** Cada puerta requiere evidencia del entorno y autorización antes de pasar a escrituras. Aunque Ubuntu ya está identificado, faltan configuración efectiva del sitio en el panel, vhost, pool y responsables; no se proporcionan ni ejecutan scripts de instalación/firewall basados en suposiciones.

Resolver Composer ausente y Node 18.20.8 incompatible mediante un procedimiento posterior autorizado o build externo compatible, sin instalar ahora. Confirmar recursos/disco y capacidad necesaria; no asignar números de RAM/CPU ni rutas inexistentes por el nombre KVM 2.
2. **Separación:** acordar cuenta/servicio, directorios de releases, configuración, clave, almacenamiento de fotos, temporales, logs, sesiones, caché/locks, base, usuarios, correo de prueba y OAuth exclusivos de staging. Si comparte VPS con producción, esa separación y los límites de recursos deben probarse; si no es posible, no iniciar staging allí. No reutilizar el arnés temporal de Windows ni sus credenciales como infraestructura de staging.
3. **Artefacto:** identificar el commit y diferencias aprobadas, incluidos documentos sin seguimiento; preparar build reproducible desde los lockfiles. En una tarea autorizada posterior, instalar dependencias sin modificar locks y construir Vite en un entorno aislado. Repetir auditorías de Composer/npm; no usar `audit fix --force`. 5. **Conexión sin escrituras:** desde el VPS y el SAPI web de staging verificar origen permitido, TLS/identidad, usuario runtime y base exclusiva. Mostrar únicamente comprobaciones saneadas. Si identidad, TLS, allowlist o aislamiento no coinciden, **detener antes de migrar o crear fixtures**. Un puerto alcanzable no satisface esta puerta.
6. **Esquema sintético y ensayo:** con permiso explícito posterior, crear esquema vacío de ensayo exclusivo con versión/configuración MySQL compatibles y aplicar las migraciones revisadas mediante identidad DDL limitada. Preparar fixtures sintéticos por un procedimiento controlado, no importar datos reales ni ejecutar seeders generales. Ensayar también actualización desde un esquema histórico sintético cuando se valide la ruta de actualización, no solo desde cero. `migrate:status` debe quedar completo hasta `2026_10_23_000002_create_report_photos` (16 archivos en esta revisión).
7. **Comprobaciones de migración:** normalización/duplicados VIN y placa, un reporte por vehículo, FK/atribución/auditoría, separación validación/caso, último administrador activo, hash de sesión única, `report_photos`, `photo_file_deletions`, sesiones/caché/locks y jobs si se usan. Las migraciones históricas cambian estados/credenciales demo: revisar sus efectos y coordinar reautenticación, nunca promover ni verificar automáticamente usuarios reales para salvar el ensayo. MySQL DDL puede quedar parcialmente aplicado; probar la recuperación, no asumir rollback transaccional.
8. **Respaldo y restauración de ensayo:** con todos los datos de staging sintéticos, producir respaldo consistente de base y fotos privadas, más identificación del artefacto y acceso separado a su configuración privada/clave estable. Guardarlos cifrados, fuera del root web y con permisos/retención acordados. Restaurar en **otra base de recuperación y otro directorio privado**, verificar integridad y acceso a fotos, conteos, permisos y auditoría. Establecer RPO/RTO y medir tiempo real. No basta producir un dump ni verificar solo su tamaño. No sobrescribir una base existente ni usar herramientas destructivas del banco local contra el servicio remoto.
9. **Rollback ensayado:** definir pausa de escrituras solo de staging, artefacto anterior compatible y recuperación ante DDL parcial. Si no basta volver al release, restaurar el conjunto base/fotos en destinos nuevos y cambiar la conexión mediante procedimiento autorizado, contemplando escrituras posteriores al backup. No prometer recuperación sin pérdida con `migrate:rollback`; algunos `down()` pierden metadatos y la retirada de credenciales no es reversible. Respaldos con datos reales o ensayo de actualización de producción requieren otra autorización y política: siguen siendo requisito posterior del checklist de producción, fuera de esta preparación sintética.
10. **Cachés y operación:** tras validar identidad/configuración y permisos del release de staging, ejecutar en una futura tarea autorizada `config:cache`, `route:cache`, `view:cache`, activar scheduler y worker solo si la decisión de cola lo exige. Los cachés de configuración contienen secretos: no adjuntarlos. No limpiar almacenes compartidos de otro entorno con `cache:clear`/`optimize:clear`. Probar arranque, reinicio de servicios y cambios de release sin perder archivos privados.
11. **Aceptación y acta:** ejecutar la matriz siguiente, adjuntar evidencia saneada y registrar responsable, fecha, versión y resultados por prueba. Resolver fallos; no convertir error de DB/mapa en «sin resultados». El operador aprueba staging solo tras cerrar las puertas y bloqueantes. La publicación de producción es una autorización posterior distinta.
